# Mandera Properties Management — ملخص شامل للمشروع

> هذا الملف ملخص كامل لكل ما تم الاتفاق عليه وتنفيذه بخصوص المشروع، من الفكرة الأساسية لحد آخر خطوة تقنية. مرجع واحد يجمع كل شي.

---

## 1. الفكرة الأساسية

نظام لإدارة العقارات المؤجرة (Property Rental Management System) لأصحاب العقارات، يساعدهم يتتبعوا:
- عقاراتهم ووحداتهم السكنية.
- المستأجرين وعقود الإيجار.
- الدفعات (مين دفع، مين متأخر).
- المصروفات على كل عقار.
- طلبات الصيانة.
- إشعارات تلقائية عن أي شي محتاج انتباه (متأخرات، عقود قربت تنتهي).

المشروع **أقرب لباك إند قوي** أكتر من كونه واجهة استخدام ضخمة — الواجهة الوحيدة اللي بتُبنى فعلياً بـ Next.js هي واجهة **Master Admin**. كل شي تاني (تجربة صاحب العقار) بيصير عبر **تطبيق موبايل Flutter** يستهلك الـ API تبعنا.

## 2. الأدوار الثلاثة بالنظام

### أ) Master Admin (واجهة ويب — Next.js)
شخص يدير **المنصة نفسها**، مش عقارات. مسؤول عن:
- إضافة حسابات جديدة لأصحاب العقارات (Owners) — **لا يوجد تسجيل ذاتي (self-signup)**، الإضافة حصراً من طرفه.
- تفعيل / تعطيل حساب Owner (مؤقت وقابل للتراجع).
- حذف حساب Owner (soft delete دائم — البيانات تختفي من كل الواجهات لكن تبقى بالـ DB للأرشفة).
- مراقبة **إحصائية فقط** (أعداد: كم عقار، كم وحدة لكل Owner) — **بدون** دخول على تفاصيل عقود أو دفعات أو مستأجرين لأي Owner (خصوصية كاملة لبيانات كل Owner التشغيلية).

### ب) Property Owner (صاحب العقار — تطبيق Flutter عبر API)
الشخص اللي فعلياً بيستخدم النظام يومياً لإدارة عقاراته:
- إضافة/تعديل/حذف عقارات.
- إضافة/تعديل/حذف وحدات سكنية داخل كل عقار (بمواصفاتها: طابق، مساحة، غرف، حمامات، قيمة إيجار).
- إضافة مستأجرين (بياناتهم، مستند الهوية).
- إنشاء وإدارة عقود إيجار (ربط مستأجر بوحدة، تواريخ، قيمة إيجار، تأمين).
- تسجيل ومتابعة الدفعات (مين دفع، مين متأخر، بأي طريقة).
- تسجيل مصروفات (صيانة، مياه، كهرباء...).
- إدارة طلبات صيانة (نوع المشكلة، أولوية، فني مسؤول، تكلفة).
- استقبال إشعارات (push حقيقية + داخل التطبيق) عن: دفعات متأخرة، عقود قربت تنتهي، دفعات جديدة تسجلت.
- الاطلاع على تقارير (إيرادات، مصروفات، صافي دخل) لفترة معينة، قابلة للتصدير PDF/Excel.

### ج) Tenant (المستأجر)
**لا يملك أي حساب أو وصول للنظام إطلاقاً.** مجرد سجل بيانات يديره الـ Owner بالكامل. أي تواصل معه (اتصال/واتساب) يصير من خارج النظام مباشرة.

## 3. الكيانات (Entities) وعلاقاتها

```
Owner (User) ──┬── Properties ──── Units ──┬── Contracts ──── Tenant
               │                            │        │
               │                            │        └── Payments
               ├── Tenants                  │
               ├── Expenses ── (Property)   └── Maintenance Requests
               ├── Notifications
               └── Device Tokens (FCM)
```

| الكيان | الوصف المختصر |
|---|---|
| **User** | ملف تعريف (profile) لكل من Master Admin و Owner، بعمود `role` يفرّق بينهم |
| **Property** | عقار (اسم، نوع، مدينة، عنوان، موقع، صورة) |
| **Unit** | وحدة سكنية داخل عقار (رقم، طابق، نوع، مساحة، غرف، حمامات، إيجار، حالة) |
| **Tenant** | مستأجر (اسم، هوية، هاتف، إيميل، صورة، مستند) |
| **Contract** | عقد إيجار يربط Unit + Tenant (تواريخ، إيجار، دورة دفع، تأمين، حالة) |
| **Payment** | دفعة مرتبطة بعقد (مبلغ، استحقاق، دفع فعلي، طريقة، حالة) |
| **Expense** | مصروف على عقار (نوع، مبلغ، تاريخ، وصف) |
| **MaintenanceRequest** | طلب صيانة (نوع مشكلة، أولوية، وصف، صور، حالة، تكلفة) |
| **Notification** | إشعار للـ Owner (نوع، عنوان، نص، مقروء/غير) |
| **DeviceToken** | توكن FCM لجهاز الموبايل تبع كل Owner (لإرسال Push) |

## 4. أهم السيناريوهات المنطقية (Business Logic)

### دورة حياة الوحدة (Unit Status)
- **شاغرة (vacant)** ← الحالة الافتراضية، أو بعد انتهاء/إنهاء عقد.
- **مؤجرة (occupied)** ← تلقائياً عند إنشاء عقد فعّال عليها.
- **صيانة (maintenance)** ← يدوية من الـ Owner، مستقلة عن حالة العقد.

### دورة حياة العقد (Contract)
1. **إنشاء عقد جديد** → يولّد تلقائياً جدول دفعات (`payments`) كامل حسب دورة الدفع (شهري/ربعي/سنوي) بين تاريخ البداية والنهاية + يحوّل الوحدة لـ"مؤجرة".
2. **اقتراب الانتهاء** → تنبيهات متدرجة تلقائية (بدون تدخل يدوي) عند **14 يوم / 7 أيام / 3 أيام** المتبقية.
3. **انتهاء العقد فعلياً** (بدون تجديد أو إنهاء يدوي) → الحالة تتحول لـ"منتهي" تلقائياً + الوحدة ترجع "شاغرة".
4. **الإنهاء المبكر (يدوي من الـ Owner)** → يلغي الدفعات المستقبلية المعلّقة + يرجّع الوحدة "شاغرة".
5. **التجديد** → **لا يعدّل العقد القديم**، بل ينشئ **عقد جديد منفصل** مرتبط بالقديم (لحفظ الأرشيف التاريخي كامل)، والعقد القديم توصف حالته "مجدَّد".

### دورة حياة الدفعة (Payment)
- تتولد تلقائياً `pending` (معلّقة) عند إنشاء العقد.
- تتحول لـ`overdue` (متأخرة) تلقائياً عبر مهمة مجدولة يومية (Cron) لما يعدي تاريخ الاستحقاق بدون تسجيل دفع.
- عند تسجيل الدفع الفعلي، تتحول لـ`paid` (مدفوعة) + إشعار فوري يتولد للـ Owner.

### الإشعارات
- تُخزَّن دايماً بجدول `notifications` (لعرضها داخل التطبيق).
- كمان تُرسل **Push حقيقي** عبر **Firebase Cloud Messaging (FCM)** لتطبيق Flutter — عبر تسجيل `device_token` لكل جهاز موبايل، ومهمة سيرفر (Edge Function) بترسل الإشعار فعلياً وقت توليده.
- **أنواعها**: دفعة متأخرة، عقد قارب ينتهي (بمستويات 14/7/3 أيام)، دفعة تسجلت، تحديث طلب صيانة.

### رقم العقد
- تسلسل **عام على مستوى النظام كله** (مش لكل Owner لحاله) — يبدأ من `10001` ويزيد تصاعدياً لكل عقد جديد بالنظام، بغض النظر مين المالك.

## 5. القرارات المعمارية النهائية

| القرار | التفاصيل |
|---|---|
| **Framework** | Next.js (App Router) — واجهة Master Admin + API Routes لتطبيق الموبايل |
| **Database** | Supabase (PostgreSQL) |
| **Auth** | Supabase Auth لكلا الدورين (Master Admin + Owner) |
| **File Storage** | Supabase Storage (صور، مستندات هوية، إيصالات، ملفات عقود PDF) |
| **اشتراكات/باقات** | لا يوجد — كل Owner له نفس الصلاحيات دون قيود |
| **رؤية Master Admin** | إحصائية/عددية فقط، بدون تفاصيل تشغيلية لأي Owner |
| **Mobile App** | Flutter (يبنيه مبرمج موبايل منفصل) |
| **Push Notifications** | Firebase Cloud Messaging (FCM) مربوطة بـ device tokens |
| **تسجيل Owner جديد** | حصراً عبر Master Admin، لا يوجد self-signup |
