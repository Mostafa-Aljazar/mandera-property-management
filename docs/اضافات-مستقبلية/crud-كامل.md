# عمليات CRUD التفصيلية (id-based) المحذوفة

**الحالة:** تم حذف الكود فعلياً (وليس مجرد تجميد). هذا الملف توثيق لما كان موجوداً ولماذا انحذف، لأجل أي عودة مستقبلية.

## لماذا انحذفت
`docs/new/openapi.yaml` المرسل من فريق الموبايل يوفّر فقط `GET`/`POST` على مستوى القائمة لكل مورد (properties, units, tenants, contracts, payments, expenses, maintenance-requests) — بدون أي مسار مبني على `{id}` للتعديل الجزئي أو الحذف أو رفع ملف مستقل. تطبيق الموبايل الحالي (المبني على Flutter، غير موصول ببيانات حقيقية بعد) لا يستدعي أي من هذه المسارات. تم حذفها بدل إبقائها معطّلة لتفادي ازدواجية الكود مع المسارات الجديدة المسطّحة.

## ماذا كان موجوداً بالضبط

| المسار القديم | الوظيفة | قابل للاسترجاع من git؟ |
|---|---|---|
| `GET /api/v1/owner/auth/me` | إرجاع بيانات المستخدم الحالي من التوكن | ✅ نعم (`git log --all --full-history -- 'src/app/api/v1/owner/auth/me/route.ts'`) |
| `GET/PATCH /api/v1/owner/properties/[id]` | تفاصيل/تعديل عقار واحد | ✅ نعم |
| `POST /api/v1/owner/properties/[id]/image` | رفع صورة عقار بشكل منفصل عن الإنشاء | ✅ نعم |
| `GET/PATCH /api/v1/owner/units/[id]` | تفاصيل/تعديل وحدة واحدة | ✅ نعم |
| `PATCH /api/v1/owner/units/[id]/status` | تغيير حالة الوحدة (متاحة/مؤجرة/صيانة) منفردة | ✅ نعم |
| `GET/PATCH /api/v1/owner/tenants/[id]` | تفاصيل/تعديل مستأجر واحد | ✅ نعم |
| `POST /api/v1/owner/tenants/[id]/photo` | رفع الصورة الشخصية بعد الإنشاء | ✅ نعم |
| `POST /api/v1/owner/tenants/[id]/document` | رفع صورة الهوية بعد الإنشاء | ✅ نعم |
| `PATCH/DELETE /api/v1/owner/profile`, `/profile/password`, `/profile/settings` | تعديل الملف الشخصي / كلمة السر / الإعدادات | ⚠️ لا (لم تكن مُسجّلة بـ git — ملفات جلسة سابقة غير مُلتزمة) |
| `GET /api/v1/owner/payments/overdue` (النسخة القديمة) | ملخص الدفعات المتأخرة | ⚠️ لا — **لكن** استُبدلت فعلياً بـ [`GET /api/v1/payments/overdue`](../../src/app/api/v1/payments/overdue/route.ts) الجديد، فلا حاجة لاسترجاعها |
| `GET /api/v1/owner/payments/[id]/receipt` | تحميل إيصال دفعة | ⚠️ لا |
| `GET /api/v1/owner/expenses/[id]/receipt` | تحميل إيصال مصروف | ⚠️ لا |
| `PATCH /api/v1/owner/maintenance-requests/[id]/close` | إغلاق طلب صيانة (مع تكلفة/اسم فني) | ⚠️ لا |
| `POST /api/v1/owner/maintenance-requests/[id]/images` | رفع صور صيانة بشكل منفصل عن الإنشاء | ⚠️ لا |

للملفات المُعلَّمة ⚠️: لم تكن هذه الملفات قد التُزمت بـ git بعد (أُنشئت بجلسة سابقة ولم تُحفظ بكومِت)، لذلك حذفها نهائي من ناحية الكود — أي عودة لها تحتاج إعادة بناء من الصفر، وليس مجرد `git checkout`.

## المطلوب لإعادة بنائها مستقبلاً (إن طلبها فريق الموبايل)
- تأكيد أن التطبيق فعلاً بحاجة شاشات تعديل/حذف مستقلة لكل مورد (لم تكن مذكورة بالـ spec الحالي).
- بناء مسارات مسطّحة جديدة (`PATCH /properties/{id}`, `PATCH /units/{id}/status`, إلخ) بنفس نمط الـ response الجديد (`openApiSuccess`/`openApiError`) بدل إحياء المسارات القديمة تحت `/owner/`.
- بالنسبة لإيصالات الدفعات/المصاريف وصور الصيانة المنفصلة: الأبسط هو دمجها ضمن استجابة القائمة/الإنشاء (كما فعلنا مع صور الوحدات) بدل مسار منفصل بـ `{id}`، إلا إذا أكّد فريق الموبايل حاجته لمسار مستقل.
